# GearSwap's tests

Lua tests of GearSwap itself and of Selindrile's framework on top of it, run by [busted](https://lunarmodules.github.io/busted/) on a plain Lua 5.1, the language Windower's LuaJIT speaks. They play a made-up character, Testy, on a stand-in for the game, and look at what a player would: what is worn, what GearSwap sends, and what the user file's hooks are handed.

```bash
dotnet run .claude/gear.cs -- test
```

runs the spec files a change could have affected, each in a busted process of its own, side by side (`.claude/tools/tests/run-gearswap-tests.cs`): those that never passed, whose own file changed since, or that loaded a file that changed or is gone. When a file every spec file rests on changes (`support/`, `fixture/res/`, `.busted`, Windower's libraries, the runner, or the names of the files the Windower install below is copied from), all of them run. `dotnet run .claude/gear.cs -- test --all` runs every spec file, as the run before a PR should, and so does `test gearswap`. `--filter <text>` runs only the tests whose name holds the text, in every spec file, and keeps no record. `.claude/tools/README.md` says how the records are kept. One file can also be run by hand from the repo root, where `.busted` sets busted up:

```bash
busted tests/sel/idle_spec.lua
```

They run on Linux or WSL, not on Windows, and need Lua 5.1, LuaRocks and busted: `luarocks --lua-version 5.1 install busted`. Nothing else: no game, no Windower, no network.

## What a test rests on

A test checks a mechanism: which set is worn when, in what order sets are laid over one another, which commands go out. It rests on GearSwap, on Sel (`libs/`), on the job files (`data/<JOB>.lua`), on the code of User-Globals.lua (its functions) and on the fixture characters, which belong to the tests. It never rests on what the user's own files hold, since those change as the user likes: User-Globals.lua's lists (trusts, food, weapon skills, buffs), mode options, defaults and binds, and the sets in the real characters' gear files under `data/Vanar/` and `data/Mytha/`. A change to any of them must not fail a test.

A test that needs one of those values sets it itself, in the booted environment and before the tick acts on it: `harness.boot`'s `user` option is a function given the user environment (`user.trust_lists = {...}`, `user.state.AutoTrustMode:options('Off', 'Long')`). A boot starts AutoTrustMode, AutoFoodMode and AutoArts, modes that act on their own, off, and the latency Sel's delays are written around at half a second, as Sel defines them whatever the user's file made of them. AutoLockstyle acts on its own too, and a boot leaves it as the file has it; the tests that count locks set it themselves. User-Globals.lua keeps Auto WS's restore weapon skills, and what it works out of Auto WS Buff's buffs as it loads, in locals no test reaches by name, so `support/user_globals.lua` gives a test its own.

## What is where

| Path | What |
|---|---|
| `gearswap/` | GearSwap with no framework: the order of an action's precast, midcast and aftercast, what the hooks are handed, commands, status and buff events, and how a set becomes equip requests (names, augments, bags, `empty`, slot names, `set_combine`). |
| `sel/` | How Sel picks and lays sets, as `docs/frameworks/sel.md` describes: idle, engaged, precast, midcast, weapon skills, abilities, the weapon lock, defense and kiting, and the hooks a gear file may define. Then the rest of Sel: its `gs c` commands, its mode class, the status box, Treasure Hunter, spell maps, and what it does on buffs, zoning, the time of day, a sub job change and a monster's actions. Last, what Sel does on its own (`auto_*_spec.lua`): its tick, the Auto modes and the lists they work from. |
| `jobs/` | What each job file in `data/` does on top of Sel, one spec per job: the set a spell, ability or weapon skill takes, what a job's hook changes or sends, its commands, the states it keeps and what its tick does on its own (Auto Buff Mode, Hasso, Majesty and the rest). They play Jobby, a made-up character with a small gear file for each job. |
| `data/` | Every character's real gear file loads under GearSwap and Sel, builds its sets and gets through a status change and an action without an error. It asserts nothing of what a set holds: it wears the starting weapon set's weapons, and uses a weapon skill the game lists whatever is in hand. It finds the gear files itself, so a new one is tested without an edit here. |
| `harness/` | Tests of the stand-ins below. |
| `support/` | The harness. |
| `fixture/data/Testy/` | Testy's user files: `Testy_WHM.lua`, a plain GearSwap file whose hooks note what they were handed; `Testy_Rdm_Gear.lua`, a small Sel gear file the real `data/RDM.lua` loads; and the other files the tests load by name. |
| `fixture/data/Corey/` | Corey's user files, `Corey_WHM.lua` and `Corey_BLM.lua`, plain files that say which they are and note what they are told to unload: for the tests of the file GearSwap loads on a job change, and, with Corey as a monipulator, which has no file, of GearSwap with no file loaded. |
| `fixture/data/Autoy/` | Autoy's Sel gear files, for the real `data/RDM.lua` and `WAR.lua`: the character the tests of Sel's automatic actions (`sel/auto_*_spec.lua`) play. What a job file adds to them, such as its own buffs under Auto Buff Mode, is tested in `jobs/`. `support/autoy.lua` holds Autoy's gear and boots Autoy. |
| `fixture/data/Commy/` | Commy's Sel gear files, for the real `data/RDM.lua`, `WAR.lua` and `THF.lua`: the character the tests of Sel's commands, modes, status box, Treasure Hunter, spell maps and event handling play. `support/commy.lua` holds Commy's gear and boot options, and the helpers those tests share. |
| `fixture/data/Jobby/` | Jobby's gear files, one per job (`Jobby_Blu_Gear.lua` and so on), which the real job files load. Each defines the sets its job file looks for with pieces that tell them apart, so a test knows from what is worn which set was chosen. `support/jobby.lua` holds Jobby's boot options, the idle sets as the game shows them worn, the weapon each job holds, what Jobby is told and types but the lines User-Globals.lua gives five seconds after his file first loads, what the job specs share (the gear file's sets, the actions sent with their targets, those of the first moments of Sel's tick, low MP, the pieces asked for in the sub slot), `jobby.abilities`, the job abilities the game gives a main job at 99 and a sub job at 49 (the lists assume each merit ability has its merits spent, since the game lists one only then), for a test whose boot gives Jobby only those and the moves of the pet or avatar out, and `jobby.weaponskill`, with which the job specs type a weapon skill when they look at what it puts on: it gives what is worn once the weapon skill has gone out, and fails the test when it didn't go out or another action did. Since the game lets him use only the weapon skills of the weapons in hand, `jobby.weapons` names one for each job whose gear file's idle set names no weapon and whose tests type a weapon skill other than hand-to-hand's, and the boot puts it in the inventory and in hand over the idle set; a spec's worn tables lay it over `jobby.idle` or `jobby.full_idle` once, at the top. A test that needs another type wears it at the boot (`wearing = {main = ...}`, or `'empty'` for bare hands) or picks a weapon set (`gs c set Weapons ...`). A job with none named holds what its idle set does, or nothing, which is hand-to-hand. |
| `fixture/data/Globby/` | Globby's files, for the real `data/WAR.lua`: `Globby-Globals.lua`, his own Globals file, which Sel loads after User-Globals.lua's and which sets the latency to 1, turns AutoArts on, and gives AutoTrustMode and AutoFoodMode an option each and turns them on, and `Globby_War_Gear.lua`, a gear file with no sets. They are for the test that a boot puts these back as Sel defines them (`harness/boot_spec.lua`). |
| `fixture/res/` | Small cuts of Windower's resource files: only the entries the tests use, each line as Windower/Resources has it. Add an entry by copying its line from there. |

## The harness

`support/harness.lua` boots GearSwap for a test as Windower loads an addon: `harness.boot(options)` returns a session whose `type`, `console`, `finish_action`, `interrupt_action`, `engage`, `gain_buff` and `advance` play the game, and whose `worn`, `traffic` and `log` say what happened. The session runs most of the game's own functions too (`set_day`, `change_zone`, `give_pet`, `send` and the rest) and lets the game settle after each. `harness.boot_updated` boots a Sel character and has Sel put on the set it picks, as Testy's, Commy's and Jobby's boots do. `support/testy.lua` holds Testy's gear and boot options, the boot the red mage's tests share, and the game's name for each slot a set may name another way.

What the session reads of the game gives what came since it last read the same thing: `traffic`, and `actions` and `action_entries` from it; `chat` (and `chat_lines`, with each line's color), `printed`, `typed` and `commands`. Each keeps its place and leaves the game's lists whole, so `log` still has every line; `forget` takes everything so far as read, as the boot does with everything up to its end. `play_until_action` plays frame by frame until GearSwap sends an action, and gives the clock when it did. `type_alone` types a line that names its action and fails the test unless that action, and no other, is what was sent since the actions were last read; `commy.cast` and `jobby.weaponskill` type with it.

- **A Lua state of its own.** Each boot gets its own environment, with its own `require`, so GearSwap's globals, the libraries it loads and the user file's globals don't carry from one test to the next. What Lua keeps for the whole state is shared: the `string` table, since Windower's string functions have to be where strings' methods come from, and the metatables of strings, numbers, booleans and functions. Each boot puts these back as Lua had them before the first, so one boot's libraries don't wrap another's.
- **A Windower install of its own.** GearSwap runs from a copy, made in the temp folder once per spec file: the repo's GearSwap (its Lua, `libs/`, and the Lua under `data/` with `fixture/data` added), Windower's libraries from `docs/windower/libs` and the resources from `fixture/res`. What GearSwap or Sel write lands in the copy, never in the repo, and the copy is removed when busted exits. Paths in an error are given back as the repo's. File names match in any case, as on Windows.
- **What a spec file loaded.** The harness notes the repo file behind each file read from the copy (`harness.loaded_files()`), and as busted exits (`support/cleanup.lua`) writes them, a path a line, to the file the environment variable `GEARSWAP_TEST_DEPS` names, if it is set. The runner sets it for each spec file, and keeps what the spec file loaded when it passed, to run only the spec files a change could have affected.
- **Windower's own libraries**, unchanged, from `docs/windower/libs`. `dotnet run .claude/gear.cs -- windower-libs` writes them from Windower/Lua at the commit `.claude/tools/lib/Sources.cs` pins; move the pin there, run it, and run the tests. Windower's C modules are stood in for: `support/pack.lua` (string.pack and string.unpack in Windower's formats), `support/bit.lua` (LuaJIT's bit), and an empty socket and mime, which GearSwap requires and never calls.
- **Windower's Lua dialect.** Windower's Lua takes a method called on a literal (`'%d':format(n)`, `0:char()`, `true:fn()`) or on a table constructor, and a function expression called where it stands. `support/dialect.lua` puts each in parentheses before a file is compiled; nothing else changes, line numbers included.
- **The game** (`support/game.lua`): the character, a monster to target, the other mobs a test adds, a pet, bags and gear, and the Windower API over them. Nothing happens on its own. What GearSwap sends is noted at once, with the items and targets it names as they stand then, and waits for the game to settle, as it would for the next frame. A packet then goes through the outgoing chunk event, and one no handler blocks reaches the server: an equip request is carried out (a piece worn in another slot moves there, and the server tells of the slot it left emptied too, the stand-in's choice; one that changes the main hand takes off a sub slot piece that no longer fits beside it), or refused for a piece the character can't wear there (in the sub slot: a weapon without the Dual Wield trait, anything but a grip beside a two-handed weapon, a grip beside anything else, anything beside a hand-to-hand weapon), and confirmed with the packets the server answers with; so is a move of items between bags (the server's side of `gs stash` and `gs pull`), which puts as many of a stack as asked on a stack of the same item with room or in the first empty slot, with the add item and remove item events, and takes nothing from or into a closed bag, a Mog House bag away from the Mog House and a moogle, or a full one. An equip request that puts a piece in the main, sub or range slot, or takes the main or sub weapon off, takes the TP, as the game does, and so does a change of main job with a weapon on. The char update tells of each change of TP, a test's own `set_tp` too, and the tp change event follows. A test that writes `game.player.vitals` itself, as the specs do for HP and MP, changes them silently: no packet or event says so, and GearSwap reads them only when it next refreshes its globals, as it does before a `gs` command or an action it handles. A TP is given with `set_tp`, or the boot's `tp` for the TP the character has when GearSwap loads; only the test of GearSwap's refresh reading the vitals writes it there itself (`gearswap/refresh_spec.lua`), since with `set_tp` the char update would hand GearSwap the TP before it read them. A command runs (a `wait` puts the rest off); chat input goes through the outgoing text event. A packet GearSwap hands Windower as the server's arrives as injected. The clock moves only when a test advances it, and the timers due then run. A test says when the server answers an action, when a buff comes or goes, when a recast starts, when Vana'diel's time, day or weather, the zone or a job changes (a change of main job takes every piece off), and when a pet (a puppetmaster's automaton, a geomancer's luopan) arrives, changes status or gains TP, or an indicolure comes or goes: `give_pet`, `take_pet`, `set_pet_status`, `set_pet_tp` and `set_indi` send the packets the server does, and `place_pet` puts out a pet with none, as one out when GearSwap loads.
  - **Other mobs**: `add_party_member` adds another player, in the party (`<p1>` on), in another party of the alliance (`slot = 'a10'`) or, with `in_party = false`, in none, and GearSwap sees them when it next looks at the party; their HP, MP and TP are on the party list only; one given `leader` leads their party (the player leads the first otherwise), and one given `alliance_leader` the alliance; `add_mob` an NPC, or with `monster = true` a monster, with a monster's id (by which GearSwap tells the two apart) and spawn type (by which Sel and User-Globals.lua do); `target` and `subtarget` aim at one, `target` with the target change event. A mob's `distance`, and a pet's, is squared, as Windower gives it, and the mob stands that far along x. Windower's mob tables give a mob's HP percent and no HP or MP, the player's own included; they carry a tp and an mpp too, which GearSwap leaves out when it copies the player's, as not the character's, and the stand-in leaves the tp out of every mob's but a pet's, which has ten times the pet's TP, as GearSwap reads it there.
  - **The battle target**, `<bt>`: the monster the alliance has claimed, none until then. A monster no one has claimed is claimed by the player when an action of theirs lands on it, or one of its own on them; a test can also set a monster's `claim_id`.
  - **What the game reports of itself**: `set_info` changes what `get_info` says (the Mog House, the target arrow); `set_automaton` and `set_species` what `get_mjob_data` says for a puppetmaster and a Monipulator; `set_job_traits` the traits `get_abilities` lists, whose weapon skills are those of the main hand's weapon type (hand-to-hand's with nothing in it) and of the ranged weapon's, or those a boot's `abilities` name, whatever is in hand. The game lists only those the character has the skill for, a relic or mythic weapon's own only with that weapon in hand (Mystic Boon with Yagrush), short of Unlocking a Myth for a mythic one's, and some others only with a merit or a quest (Requiescat, Savage Blade). The stand-in models none of these: it looks at no skill levels, merits or quests, and the resources don't name a weapon skill's weapon, so it lists every one of the type. The game lists only the job abilities of the main job and the sub job at their levels, and of the ready moves and blood pacts only those of the pet or avatar out; the resources give no job, level or pet for a job ability, so unless a boot names them the stand-in lists every one. `start_ability_recast` and `start_spell_recast` the recasts. A bag with `disabled` set is closed; a game with `refuse_moves` or `refuse_equips` set refuses every move or equip request; `loading` set to `'player'` or `'job'` has `get_player` report a character the game is still loading. `turns` lists the angles the character was turned to.
  - **Packets**: the game writes most of the packets the server sends byte by byte. `send` builds one from Windower's own field definitions, by label, so each lands where the real game puts it: `gs:send(0x00A, {['Zone'] = 230})`; `send_zone_in` lays labels over the zone-in packet for the game as it stands, and `receive` sends a packet's bytes as they are.
- **A plain user file** (`support/plain.lua`): Testy as a white mage on one of the plain GearSwap files in `fixture/data/Testy/`, a refresh of GearSwap's globals, and a look at the events and the hooks' calls such a file notes; Corey, on a file of Corey's own or with no file loaded.

## Adding a test

- Start with a test that fails for the reason the change is needed. A test that needs the game to do something it doesn't yet fails for want of it; add that to `support/game.lua` or `support/harness.lua`.
- Boot in the test or a `before_each`, so each test starts from the same place. Give the boot only the items the test needs.
- Pin what GearSwap and Sel really do. When they do something else than `docs/frameworks/sel.md` says, settle which is right before writing the test.
- A file runs in a process of its own, so several smaller spec files finish sooner than one big one.
- A spec file rests on the files it loads through the copy, which a boot does, and on the files every spec file rests on. Have a test read what it checks through the copy; a repo file it reads straight from the repo is one a change could leave the spec file unrun for.
