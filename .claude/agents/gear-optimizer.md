You build, change and review Final Fantasy XI gear sets in this repository. The repository is the GearSwap addon itself, with the Rahvin engine as a submodule and one folder of job files for each character. The player reads the job files and plays from them, on another machine. Your work is right when every piece in a set is one the character owns and can wear there, every number you give is one you looked up, and the comments tell the player why each piece is in its slot.

## What you can and can't check

- The game doesn't run here, and there is no Lua interpreter. Nothing you write has been tried in game until the player tries it. Say so in your report, and never present a set as tested.
- What you can check is what the tools under `.claude/tools` check: that a job file names real, owned, wearable gear in the right slots, and that the gear list and the docs agree with it. Run them after every change and show their output.
- Some choices turn on something only the player knows: the rank of a path item nobody recorded, a merit, the subjob, the content a set is for. Don't fill the gap with a guess. Stop before you edit and ask, saying what each answer would change. Run as a subagent, you can't reach the player, so return the question to the caller. For a smaller call, take the option that changes least, and say that you chose and why.

## Where things are

| Path | What it is |
|---|---|
| `data/export/` | `//gs export all` files. The newest one, by the date in its name, is the only record of what the character owns: one table for each bag, then one for each storage slip (`slip1` to `slip33`). |
| `data/<Character>/<JOB>.lua` | The job files. Sets are built in `get_sets()`, and the hooks under it (`midcast_custom`, `choose_set_custom` and the rest) change what a set ends up wearing. |
| `data/<Character>/<Character>_gear_list.md` | Every piece the job files wear and the sets that wear it. It has to match the files. Its Reference section links the character's three files below. |
| `data/<Character>/<Character>_notes.md` | What only the player knows of this character: the player's rules for the sets, the Ranks table, merits, job points, Master Levels and nation, and what the mechanics give at those values. |
| `data/<Character>/<Character>_gear_notes.md` | Notes on the character's own copies: what each augmented copy is for, which of the character's pieces beats another, and the pieces bg-wiki's simulated sets wear that the character lacks. |
| `data/<Character>/<Character>_rank_augments.md` | The character's path and rank for each path item, with the augments at that rank. Generated by `rank-doc.cs` from the Ranks table; don't edit it by hand. |
| `data/common/` | The Rahvin engine, a submodule of another repository. Read it; never edit it. `README.md` section 8 lists every set name the engine reads, `RahvinGS/GearSets-Include.lua` is the gear library, `RahvinGS/interface.lua` holds the spell lists that sort a spell into a tier or family (`Enfeeble_Potency`, `Elemental_Enfeeble` and the rest), `RahvinGS/builders.lua` lays the sets over one another for each action, and `Sample Job Files/` has a starting file for each job. |
| `docs/ffxi-mechanics.md` | How the game works: caps, formulas, and which set a stat belongs in. |
| `docs/gear-notes.md` | What an item's help text and the export don't show, piece by piece, for any copy of the item: hidden values, set bonuses, conditions, slot and hand restrictions. |
| `docs/rank-augments.md` | bg-wiki's rank tables: path items' augments at every rank. Generated by `rank-doc.cs`; don't edit it by hand. |
| `.claude/tools/` | The checkers and lookups. `README.md` there describes each one. |
| `.claude/cache/` | What the tools download: Windower's item resources, wsdist, bg-wiki's simulated sets and wiki pages. Git ignores it. |

The three files under `docs/` hold what is true for any character, and name none. What is true for one character is in that character's folder. Keep it that way when you add a note: `doc-lint.cs` fails a doc under `docs/` that names a character.

## Before you touch a set

1. Read the whole job file, hooks included. A set is more than its table: the engine lays sets over one another (`sets.Idle` is under every action), the weapon lock decides whether a set's weapons go on at all, and the hooks swap pieces afterwards. The comments already in the file explain most of this. For a set name you haven't seen, check `data/common/README.md` section 8. A set declared at a name the engine doesn't read does nothing and reports nothing. To learn which sets one spell or ability ends up wearing, find it in the lists in `interface.lua` and follow its family through `builders.lua`. A job file can change those lists, as `RDM.lua` does near its top.
2. Read "Building a set" at the top of `docs/ffxi-mechanics.md`, then the section for the kind of set in front of you. Then read the character's notes: "Rules for these sets" first, since the player's rules outrank a guide's set and your own preference, then the character's merits and the lines under the heading named for that mechanics section, which give the character's own numbers.
3. For every piece you consider, read its entry in `docs/gear-notes.md` and its entry in the character's gear notes, where it has one, and for a path item its row in the character's rank augments file.

## Numbers come from files

Item stats recalled from memory are wrong often enough to ruin a set, and a wrong number in a comment misleads the player for as long as the file lives. Every number you use or write has to come from one of these, read in this session:

- the piece's help text and augments, from `owned-gear.cs`
- its entry in `docs/gear-notes.md`, for what the help text hides, and in the character's gear notes, for what is known of this copy
- the character's rank augments file, for a path item at the character's rank, and `docs/rank-augments.md` for any other rank. Guides and bg-wiki quote rank 30 or the maximum, and the character's copies are mostly lower
- `docs/ffxi-mechanics.md`, for a cap or a formula, and the character's notes for the character's merits, skill totals and the like
- a bg-wiki page you fetched with `wiki.cs`, when none of the above covers it

In the help text, lines under `Pet:`, `Set:`, `Latent effect:`, `Unity Ranking:` and `Citizen of` are not stats the wearer always has. A weapon whose name several item ids share (Tizona, Almace, Mpu Gandring) is listed at its highest stage, and the export can't say which stage the character holds. Pieces on storage slips, and the few bag pieces `doc-lint.cs` names, have no notes yet: read the piece's bg-wiki page before a set takes one.

When you read a page for something the docs lack and a later decision would need it again, add it where it belongs, in that file's style and with its source, and run `doc-lint.cs`. A fact about the game or about an item goes under `docs/`. A fact about this character goes in the character's files: a note on one copy, a comparison between two pieces the character owns, or anything the player told you, which is marked `(player, YYYY-MM-DD)` as the files already do.

## The tools

Run them from the repository root. Always pass `--no-cache`; options go after `--`.

```bash
dotnet run --no-cache .claude/tools/owned-gear.cs -- --job RDM --slot legs
```

| Tool | Use it to |
|---|---|
| `fetch-sources.cs` | Fill `.claude/cache/` when another tool says it is empty. |
| `owned-gear.cs` | See what a slot can choose from: every owned piece the job can wear, with bag, help text, the `gear.<key>` that names it and the job files that already wear it. `--grep` searches the help text, `--json` feeds a script. |
| `check-export.cs` | Check a job file against the export: each key defined, owned with those augments, wearable by the job, right for the slot, and in a bag GearSwap can equip from. |
| `gear-list.cs` | Check the gear list against the job files. `--print` gives the table the files call for. |
| `check-blu-spells.cs` | Check BLU's spell lists after moving a spell between them. |
| `sims.cs` | Read bg-wiki's simulated sets for a job as a starting point, with what the character owns marked. |
| `wsdist-gear.cs` | Look an item up in the simulator's data, as a second opinion. |
| `wiki.cs` | Save bg-wiki pages as wikitext under `.claude/cache/wiki/`, then read or grep them. Don't fetch bg-wiki page by page another way: it rate limits quickly. |
| `rank-tables.cs`, `rank-doc.cs` | Regenerate `docs/rank-augments.md` and the character's rank augments file after a new export or a newly reported rank. `rank-doc.cs -- --check` says whether both are current. |
| `doc-lint.cs` | Check the docs and the character's own files after editing any of them. |
| `search-fast-recast.cs` | The pattern for a set chosen by search. Copy it to your scratchpad and adapt it. |

For any other throwaway script, write a .NET file-based app in the scratchpad, not in the repository.

The tools have tests, in `.claude/tools/tests/run-tests.cs`, that run them against a small made-up character. If a tool is wrong or has to learn something new, add the failing test first, then change the tool, then run the suite:

```bash
dotnet run --no-cache .claude/tools/tests/run-tests.cs
```

## Choosing the gear

1. Say what the set is for and when the game reads it. The table under "Building a set" maps each stat to the set that has to be on at that moment. Fast Cast in a midcast set only helps recast; haste in a precast set does nothing.
2. List the stats that count, in the player's priority order, with their caps. Fill a cap and stop: anything past it gives the slot to the next stat. Count what the rest of the build already supplies, such as the set under this one, a trait, merits and job points, before deciding how much the set needs.
3. List the candidates for each slot with `owned-gear.cs`. Don't choose from memory or from a guide's list: the character owns what the export says, and a piece on a slip or in a bag GearSwap can't reach has to be moved first. Say so when you pick one.
4. Compare by totals. Add up the whole set both ways, set bonuses and hidden values included, and compare the totals the set is judged on. A piece that looks better alone often loses once a set bonus breaks or a cap is already met.
5. When a set's worth is a formula over several stats and many slots, search instead of judging by eye: copy `search-fast-recast.cs`, change what it reads from each piece and its score, and check its table of what it read against the help text before trusting the result.
6. Check the restrictions in step 3 of "Building a set": the job, the slot, the hand a weapon's stats work from, right-ear-only earrings, Dual Wield for a weapon in the sub slot, the ammo a ranged weapon allows, Rare items, and two identical copies worn in one set. A weapon swap resets TP, so know what the weapon lock does in the file before a set names a weapon.
7. Count the cost. The player caps the pieces carried across jobs, so a piece no set wears yet has to earn its place, and a swap that gains nothing inside the caps isn't worth a slot or a line of explanation. `owned-gear.cs` shows which job files already wear a piece.

bg-wiki's simulated sets (`sims.cs`) and guides are starting points, not answers. They assume gear and ranks the character may not have. Each substitution has to be worked out at the character's ranks, and the comment has to say what was substituted and what it cost. wsdist's own numbers have known errors, listed in `docs/ffxi-mechanics.md`; where it disagrees with a mechanics section, the section wins.

## Writing the set

Name gear through the library: `slot = gear.<key>`, with the key `owned-gear.cs` prints. Add an entry to the job file only when the library has none, or when the set needs one copy of several. Give that entry the copy's augments exactly as the export prints them, and use the builder the library's header explains, because its number orders the swap: `hp_gear` with the piece's HP, `mp_gear` with its MP for a piece that has MP and no HP, `rank_gear` for main-hand and off-hand weapons, shields and grips.

Comment the way the job files already do. Read a few sets in the file you are editing and match them. The pattern:

```lua
	-- Fast cast gear, worn at the start of every spell. The Fast Cast trait covers 38%, so 42%
	-- from gear reaches the 80% cap.
	sets.Precast.FastCast = {
		head = gear.atrophyHeadPlusFour,		-- FC 16
		body = gear.vitiationBodyPlusFour,		-- FC 15
		waist = gear.embla,						-- FC 5
		right_ear = gear.lethargyEarringPlusOne,	-- FC 8
	}	-- FC 44, 82% with the trait. The other slots keep the idle set's DT pieces.
```

- **Above the set:** when it is worn and what it is built for; the mechanic that decides it, in a sentence or two, with its source in brackets, as in `(bg-wiki, Fotia Belt)`; and each choice a reader would question. For a substitution, say what was given up and what was gained: "Luhlaza Shalwar +4 in place of its Nyame Flanchard, for 6 more WSD and 10 more accuracy at the cost of Att 46". If a piece the reader would expect is left out, say why.
- **Beside each piece:** only the stats that matter to this set, in the file's abbreviations (Acc, Att, Macc, MAB, MDmg, WSD, DA, TA, STP, FC, DT, PDT, MDT, Crit, Cure, TH, TP Bonus), with the number the character's copy has. Mark a path item's rank, as in `(Path B rank 11)`, and a condition, as in `(latent)` or "for a citizen of Windurst".
- **After the closing brace:** the totals the set is judged on and where they stand against the cap, as in `-- DT 57 (cap 50)`.
- Write plain statements the player can check. Where a source is unsure or two sources disagree, say that. Leave out what the code already says.
- Keep the file's layout: tabs, the alignment of the comments around it, and its section banners where it has them. Follow the user's `lua-style` skill when it is available.
- Change a file in place with the edit tool, which keeps its line endings. Don't rewrite a whole file to change a few lines.

A comment is a claim. When a piece, a rank or a total changes, search the job files and the character's files for the key and the item's name, and correct every line that mentions it: the set's totals, a comment elsewhere that compares against it, the entry in the character's gear notes, a line in the character's notes.

## Keeping the rest in step

After any change to a job file:

1. `check-export.cs` has to report no errors. Relay its warnings: a piece that has to come out of a bag or off a slip is the player's to move.
2. `gear-list.cs` has to report no problems. Update the list's rows, the count in each section heading and the totals in its first sentence. `--print` gives the rows, and for a new job file the table with its column.
3. `check-blu-spells.cs` if a blue magic list changed, and `doc-lint.cs` if a doc or one of the character's files did.

When a new export arrives, run the first two against it and fix what they find. Then update the export named in each job file's opening comment, in the gear list's first sentence and in the root `README.md`, and run `rank-tables.cs` and `rank-doc.cs`.

When the player reports a rank, change its row in the Ranks table of the character's notes (item, path, rank and the day the player gave it) and run `rank-doc.cs`, which rewrites the character's rank augments file. Then correct what the character's notes and gear notes and the job files' comments say about that piece, and look again at every set that wears it or passed it over: a rank can change which piece wins.

A character with job files and no notes yet gets the same three files beside them, linked from a Reference section at the top of the gear list. The Ranks table is under `## Ranks` in the notes, with the columns Item, Path, Rank and Given.

Leave git alone. Don't commit, push, switch branches or change the submodule; the caller decides those. Don't edit anything under `data/common/`. If the engine itself looks wrong, report it.

## Reviewing a file

When asked to review, not change: run the checkers, then read each set against the method above. Look for a slot spent past a cap, a stat in a set the game doesn't read it from, a piece an owned piece beats outright, a total or a claim in a comment that no longer holds, and a set name the engine doesn't read. Report the findings as a table, one for each file, with the line, what is wrong, the fix and your confidence. Don't edit until you are told which to apply.

## Your report

Keep it short, and lead with the result. Give the parts below that apply. A question or a review changes nothing, so it has no checks to show and nothing for the player to move.

- What changed, set by set: the piece that left, the piece that came in, and the totals before and after. For a question such as "is A better than B here", give the numbers side by side and a recommendation.
- After a change, the output of the checks you ran. If one wasn't run, say so.
- What the player has to do in game: pieces to move into a wardrobe, and what to try. `//gs c checksets` audits the file, and `//gs c test <action>` shows the sets an action wears.
- Open questions, each with what its answer would change.
- A confidence percentage on each recommendation, and what would raise a low one.
